## 3. Resources and availability

Provide one default preset for each resource type: Mana, Rage, Focus, Energy and PSI / Soul Points. This covers the relevant classes dynamically; do not create a duplicate aura for every class combination.

Availability is separate from value. An active resource at zero is still an active resource. Never use current > 0 as the loading condition. On class changes, login and other relevant lifecycle changes, resolve which resource pools are actually active and update or unload the matching auras.

In RoM, UnitMana is the primary-class resource slot and UnitSkill is the secondary-class resource slot. They are not synonyms for mana and energy. Resolve the slots using UnitManaType and UnitSkillType: the existing project's mapping is 1 = mana, 2 = rage, 3 = focus, 4 = energy. Read the corresponding current and maximum values from the matching slot. Inspect the current implementation and client conventions rather than relying on old comments or guessing from class names.

Account for primary and secondary resources. Avoid displaying the same typed resource twice when both slots describe the same pool. Treat a missing API, invalid value, unsupported type or unavailable pool as unavailable, not as a full resource. Obtain bar maxima from the actual resource data instead of assuming every bar has a maximum of 100.

PSI needs its own applicability check. For standard RoM, it belongs to the active primary Warlock, whose class token is HARPSYN. Verify the available class API and current client contract. A Warlock secondary class, the existence of the global GetSoulPoint function, or a returned zero must not by themselves activate a PSI aura. Non-Warlocks must not load an empty soul-point display.

GetSoulPoint returns the current count and a Willpower status; its second return is not the resource maximum. The reviewed project uses a standard range of 0–6. Keep the cap in one small resource provider/configuration point, using a reliable native maximum if the target client exposes one, otherwise the verified standard cap of six. Do not invent an API or encode the cap into the artwork. Normalize the provider's output once so rendering and conditions consume the same valid count, cap and availability.

## 4. Required PSI presentation

The default PSI style is a native number plus exactly one instance of the approved cyan diamond for each existing soul point.

- Unavailable resource: hide the whole aura.
- Available with zero points: show only the number 0. No diamonds, empty diamond outlines, ghost cells, bar, background frame, glow or Max label.
- Available with N points: show the native count N and exactly N cyan diamonds.
- Available at its valid maximum: show the number, those diamonds and the separate yellow italic cartoon-style Max label.

Do not render six fixed empty slots and light some of them. The user specifically wants a diamond added for each point that exists. Keep the number's positioning stable and use consistent pip spacing. Render the count with the existing native text facilities, not image digits or a new font dependency.

Also offer a PSI bar option in the same aura's existing display/style controls. This changes the presentation of the same resource; it does not create another independently configured aura or evaluator. The zero rule still applies: at zero, the PSI bar and frame disappear and only 0 remains. At nonzero values, show the selected bar style and live count. The same Max policy applies.

## 5. Max label rules

Use the supplied yellow italic Max artwork as a separate overlay. It is eligible only when the resource is available, its maximum is valid and greater than zero, and current >= maximum.

Apply these exact exceptions:

- Mana: never show Max.
- Energy: show Max at full only while out of combat. Suppress it throughout combat, including when energy stays full.
- Rage, Focus and PSI: show Max at full while the resource is applicable.

A combat transition must update the Energy Max overlay even if the resource value did not change. Hide the overlay as soon as the resource drops below cap or becomes unavailable. Reuse the existing combat state/events or shared update mechanism. Do not play sounds, execute custom code or animate a permanent attention-grabbing effect merely because the resource is full.

## 6. Three useful bar styles

Add a small, coherent set of options to the existing bar style selector:

1. Beveled Metal: separate metal frame with the bevel fill.
2. Glass: glass fill with a restrained native border.
3. Minimal: existing Square_FullWhite/flat fill with a native border.

Use the reference boards for proportions, layering and palette. Tint fill layers through the existing rendering facilities where suitable. The artwork is shared across resource types and classes. Avoid creating many redundant colour files.

Keep the frame and ornaments at their full display size while the fill changes. In the reviewed renderer, changing fill width resizes the whole fill texture; inspect the latest implementation and ensure decorative ends stay in the separate fixed frame layer. Reuse width-based filling for these simple stretch-safe textures where it already works. Add UV cropping only if a concrete visual problem requires it; do not replace the bar renderer just to add these styles. Preserve vertical/reverse options if the current renderer already supports them.

Expose only controls that help users: style, colour where appropriate, dimensions, text, and the PSI diamonds/bar choice. Give each relevant selection a concise mouseover explanation. Keep these in the established Field editor and retain the current section scrolling/collapse behavior.
